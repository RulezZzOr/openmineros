# Open-source and web leads for BM1398 / Zynq FPGA: 2026-10-10

Search and read-only clone of public repositories. Nothing from the miners
was copied here.

## What the repositories show

| Repo (shallow clone) | Last commit | BM1398 | Zynq FPGA register base |
|---|---|---|---|
| [braiins/zynq-io](https://github.com/braiins/zynq-io) | 2018-09-21 | no | Braiins IP map: GPIO `0x41200000`, PWM `0x42800000`, VID `0x43C50000`. Used to document the bitstream, not the stock Bitmain one. |
| [polprog/antminer_zynq](https://github.com/polprog/antminer_zynq) | 2023-03-19 | no | Only `reg = <0x0 0x40000000>` in a U-Boot DTS, which is a memory node, not the FPGA window. The bootlog is a generic Zynq boot. |
| [GPTechinno/bm13xx-rs](https://github.com/GPTechinno/bm13xx-rs) | 2025-10-17 | no (crates `bm1366`, `bm1370`, `bm1397`, `bm13xx-protocol`, `bm13xx-chain`) | not applicable |

Conclusion: none of the three contains BM1398 register or init code. The
bm1397 crate is the nearest open Rust base. Whether its frame protocol matches
BM1398 is **unverified**.

## Web sources

- [D-Central: inside the Zynq FPGA, how an Antminer control board talks to its hashboards](https://d-central.tech/inside-the-zynq-fpga-how-an-antminer-control-board-talks-to-its-hashboards/).
  Vendor blog. Claims: user space reaches the FPGA through `bitmain_axi.ko`,
  which creates `/dev/axi_fpga_dev`; a second module `fpga_mem_driver.ko`
  handles DMA; the register space is at `0x43C00000`; the bitstream
  (`soc_system.rbf`) is RSA-verified against eFuse keys, so a custom FPGA image
  is probably not possible on locked boards. **Not verified against source.**
  Note the conflict: our VNish 1.2.7 analysis found the window at `0x40000000`,
  and the `/dev/mem` path, not `/dev/axi_fpga_dev`.
- [D-Central BM1398 glossary](https://d-central.tech/mining-glossary/bm1398/).
  Says chip ID `0x1398`, 76 chips per board on an S19, and a dsPIC33EP voltage
  controller. The S19 hashboard reference says PIC U3. These two disagree, so
  the controller is unresolved.
- [D-Central: S19 hashboard reference](https://d-central.tech/asic-hashboard-reference/).
  Lists 3 boards and 76 chips per board, but not the register map.
- [Newegg listing for BM1398 chips](https://www.newegg.com/p/3GG-001F-000J2).
  Commercial listing, not evidence of anything.

No Bitmain primary source (datasheet, driver, or hashboard tool documentation)
turned up. Searches for a Bitmain `fpga.c`, a `bitmain_axi` source tree, and a
BM1398 driver returned no code.

## 88 versus 76 chips

- **76 per board** is what the miners report. Unit `.41` showed 76 on all
  three boards on its dashboard. Unit `.47` lists 76 chips on each chain in
  its API, and `chain#3 - 76 chips detected` appears in its log.
- **88** appears in two places in DCENT_OS, and neither is a BM1398 S19 board:
  - `BHB42801` hashboard SKU, `chip_name: "BM1362"`, `chips_per_chain: 88`
    (`dcentrald/dcentrald-silicon-profiles/src/hashboards.rs`).
  - Manifest label `"S19 (88-chip)"`, `chip_family: "BM1398"`, which names
    stock Bitmain S19 firmware `Antminer-S19-merge-release-20221227070716`
    (`dcentrald/dcentrald-api/assets/stock-bitmain-manifest.json`). This is a
    catalogue label with no hardware evidence in the repo.
- Public sources
  ([D-Central S19 specs](https://d-central.tech/hardware-guides/antminer-s19-specs/))
  give 76 BM1398 chips per board for the base S19 and 114 for the S19 Pro, and
  they cite no 88-chip BM1398 board.

Conclusion: 76 is what the measured units report. The 88 figure belongs to a
BM1362 board in DCENT's code and to an unexplained manifest label. Do not use 88
for the BM1398 driver.

## What this means for the open questions

1. **FPGA base:** the Braiins/D-Central value (`0x43C00000`) and the VNish
   value (`0x40000000`) disagree. The only way to settle it is a read on real
   hardware: `devmem 0x40000008 32` against `devmem 0x43C00008 32` on a unit
   running VNish. The `.47` unit runs VNish 1.2.7, so it is a valid target.
2. **HW version `0x4000b031`:** still unlinked to any register name. Matching it
   to word 2 of the window needs the same read.
3. **BM1398 protocol:** no open source gives the BM1398 frame format. The
   closest open Rust code is `bm1397`. Treat any port as a hypothesis until it
   is checked against a chip on the bench.
